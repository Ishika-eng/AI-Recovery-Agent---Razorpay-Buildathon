System architecture

Universal payment recovery & reconciliation platform

Four diagrams, each showing one mechanism: how an inbound provider event becomes a governed recovery decision, how the data model keeps "what's owed" separate from "which transaction," how a request gets from an anonymous browser to a merchant's own scoped dashboard, and how the deployed system actually reaches Postgres, an LLM, and Razorpay's real API in production.

01

Ingestion → decision loop → resolution

Every provider webhook goes through the same pipeline regardless of shape. The loop in the middle is what actually runs the recovery agent — AI proposes, policy gates, nothing executes without passing both. The bottom box is the one the whole system exists to protect: it's reachable from three different paths, and whichever gets there first wins.

02

The data model reasons about obligations, not transactions

A PaymentObligation can accumulate attempts from every provider it's tried on. Only its own status field is allowed to say "resolved" — no attempt, however it succeeded, gets to declare that on its own.

03

One login, one scoped dashboard, checked twice

A request for /dashboard is gated optimistically at the edge — cookie-only, no database — and then again where it matters: the page itself re-verifies the session and pulls only that merchant's rows. Every mutating route repeats the ownership check independently.

04

Where each piece lives

LayerFile(s)Responsibility
Provider adapters src/lib/providers/*.ts Verify signature, parse, normalize into UniversalPaymentEvent. One file per provider.
Merchant adapter src/lib/merchants/*.ts Translates a merchant's own business record into a normalized ObligationContext.
Recovery engine src/lib/engine.ts Correlation, the recovery cycle, execution, and atomic cross-channel resolution.
AI decision layer src/lib/ai.ts Structured proposal only — same input/output contract a real model call would use.
Policy engine src/lib/policy.ts Deterministic guardrails; final word on every action, independent of how the AI arrived at it.
Auth & session src/lib/session.ts, src/lib/dal.ts, src/proxy.ts Signed JWT cookie sessions, verified via a Data Access Layer, gated at the edge and again per-page.
Data prisma/schema.prisma Postgres (Neon) — the obligation-centric model above. Started on SQLite locally; moved because Vercel's serverless functions have no persistent disk for a local DB file to survive on.
Message personalization src/lib/llm.ts, src/lib/voiceScript.ts, src/lib/actions/index.ts A real LLM (Groq) writes the Hinglish voice script and email tone when configured, falling back to a fixed template otherwise. Never originates the amount, the payment link, or the unsubscribe line — those are always appended by code.
Real payment delivery src/lib/actions/paymentLink.ts, email.ts Creates a real Razorpay Payment Link and sends real email via SMTP when credentials are configured; reports a clearly-labeled simulated outcome otherwise, never throws.
05

Deployment topology

The app runs on Vercel; the recovery cycle's autonomy depends on something calling /api/cron/tick on a schedule, and Vercel's free tier only allows a daily cron — too coarse to demo cases actually advancing. A GitHub Actions workflow fills that gap for free, from inside the same repo a reviewer can already read.
